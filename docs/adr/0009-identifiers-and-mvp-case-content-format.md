# ADR-0009: Identifiers and MVP case content format

Status: Accepted  
Date: 2026-10-22  
Work item: MVP-00

## Context

AGENTS.md requires opaque UUID public identifiers and forbids exposing
sequential database IDs. `docs/IMPLEMENTATION_PLAN.md` section 12 leaves the
structured case editor open, and MVP-07 needs a stored case format that later
rich-content work can extend without rewriting history.

## Decision

### Identifiers

- Every table's primary key is a `uuid` generated by the application as
  UUIDv7 (time-ordered for index locality). Identifier generation goes through
  an injected generator interface for deterministic tests.
- No `serial`/`identity` column is used as a primary or foreign key, and no
  sequential number is exposed as an identifier.
- UUIDv7 embeds creation time with millisecond precision. This is accepted
  because `createdAt` is visible to anyone who can read the resource; it does
  not grant access and is not guessable enough to enumerate.
- Projects have a human-readable `code` (2-10 uppercase letters/digits,
  starting with a letter, unique per workspace). Cases have a per-project
  display number shown as `<code>-<n>` (for example `WEB-42`). The display key
  is a label: it can be resolved only within a project the caller can already
  access, and it never replaces the UUID in API paths.
- Composite foreign keys include `workspace_id` so a row cannot reference a row
  in another workspace.

### Case content in the MVP

- Text fields (description, preconditions, step action, step data, step
  expected result, comments) are plain text, up to 10,000 characters each,
  rendered with line breaks and automatic links only. No HTML or Markdown is
  stored or rendered in the MVP.
- Steps are an ordered list of `{ action, data, expectedResult }`, 1-200 steps,
  stored inside the immutable case revision.
- A revision stores its content as a versioned JSON document
  (`{ "schemaVersion": 1, ... }`) plus extracted plain-text columns for search.
  Later rich-text support adds `schemaVersion: 2` and a sanitizing renderer;
  version-1 documents remain valid forever.

## Consequences

- No rich-text editor dependency is selected in the MVP, and stored XSS through
  case content is structurally excluded.
- Display keys need a per-project counter maintained transactionally; gaps are
  allowed.

## Alternatives considered

- UUIDv4: rejected for primary keys because of index fragmentation; acceptable
  only for values that must not reveal time, such as token lookup IDs (which use
  random bits per ADR-0006).
- Markdown in the MVP: rejected; it needs a sanitizer and renderer review that
  belongs with the deferred rich-content work.
